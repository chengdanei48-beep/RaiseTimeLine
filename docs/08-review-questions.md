# 08. 技術理解の確認問題


## 第1章: 認証・認可とセキュリティ(8 問)

### Q1. セッション認証とトークン認証

「セッション認証」と「トークン(JWT)認証」の違いを説明してください。また、このアプリで JWT を採用した理由(利点)も述べてください。

**回答**

セッション認証は、サーバーがセッションを保存し、Cookie の ID で本人を引きます。JWT 認証は、署名付きトークンに本人情報が入っていて、サーバーは署名を検証するだけで済みます。

サーバーが状態を持たないので水平スケールしやすいことと、フロントとバックエンドを分けた SPA に向いていることです。


### Q2. アクセストークンとリフレッシュトークン

以下について説明してください。

- なぜトークンを 2 種類に分けるのか
- アクセストークンの有効期限が短い理由

(アクセストークン: 15 分 / リフレッシュトークン: 7 日)

**回答**

役割を分けるためです。

アクセストークン(15 分)は API 呼び出しごとに送るので、漏れる機会が多いです。有効期限を短くして、漏えい時の被害時間を限ります。
リフレッシュトークン(7 日)は更新時だけ使います。HttpOnly の Cookie に置き、JavaScriptから読めなくし、xssでの直接窃取をかなり減らせます。


### Q3. パスワードのハッシュ化

「ハッシュ化」と「暗号化」の違いを説明してください。また、なぜパスワード保存にハッシュ化を使うのか述べてください。

**回答**

暗号化は鍵があれば元に戻せますが、ハッシュ化は一方向で元に戻せません。

パスワードは「照合できれば十分で、復元は不要」なので、ハッシュ化します。DB が漏れてもパスワードを分からなくするためです。


### Q4. 認可(Authorization)

「認証」と「認可」の違いを説明し、「自分の投稿のみ編集・削除できる」機能がどちらに該当するか答えてください。

**回答**

認証は「誰か」の確認で、認可は「何をしてよいか」の判定です。

「自分の投稿のみ編集・削除できる」のは認可です。ログイン済みであること(認証)に加えて、投稿の持ち主と一致するかを見ます。


### Q5. CORS 設定の実務理解

以下について説明してください。

- 本番環境での CORS 設定の変更点
- `allowedOrigins("*")` の問題点

**回答**

開発中は、すべてを許可(localhost)から、本番では、実際のドメインだけを許可します。

アスターリスクを入れると任意のサイトからAPIを呼べてしまうので、悪意あるサイトがアクセス出来てしまい情報漏洩のリスクがある。


### Q6. SQL インジェクション

SQL インジェクションとは何か説明してください。また、MyBatis で防ぐための実装上の注意点を述べてください。

**回答**

SQL インジェクションは、入力値が SQL の構文として解釈され、不正な操作をされる攻撃です。

MyBatis では、`#{}`(プレースホルダ)を使えば値がバインドされて防げます。`${}`(文字列を直接埋め込む)は避けます。このアプリの XML マッパーには `${}` がありません。ORDER BY や表名のように動的に変えたい箇所は、サーバー側の許可リストで固定します。


### Q7. XSS(クロスサイトスクリプティング)

以下について説明してください。

- `<script>alert('攻撃')</script>` が投稿された場合のリスク
- React での対策方法

**回答**

`<script>` が投稿として保存・表示されると、閲覧者のブラウザで実行されます。トークンの窃取や、なりすました操作につながります。

React は、JSX で埋め込む文字列を自動でエスケープするので、既定で防げます。さらに次の対策を足します。

- `dangerouslySetInnerHTML` は使わない。
- ユーザー入力から URL を作るときは `javascript:` を弾く。
- CSP を併用する。


### Q8. HTTPS と本番セキュリティ

以下について説明してください。

- ALB を使った場合の SSL/TLS 証明書の配置場所
- ALB〜バックエンド間通信の HTTPS 必要性

**回答**

SSL/TLS 証明書は ALB に置きます。ALB でユーザーとの HTTPS を配置します。

ALB からバックエンドへの通信は、同じ VPC の中なので HTTP でも成立します。ただし、機密性の要件が高い場合や、規制がある場合は、バックエンドまで HTTPS にします。学習用なら、まず終端だけで十分です。


## 第2章: アプリケーションアーキテクチャ(7 問)

### Q9. レイヤードアーキテクチャ

Controller / Service / Repository の役割を説明してください。また、以下も答えてください。

- なぜ分離するのか
- Controller と Service の責務の境界

**回答**

- Controllerは、HTTP の入出力(リクエストの受け取り、検証、ステータス)。
- Serviceは、業務ルールとトランザクション。
- Repositoryは、DB アクセス。

分離する理由は、変更の影響を局所化し、層ごとにテストできるからです。

境界は「HTTP の知識を Service に持ち込まない」ことです。


### Q10. DTO パターン

エンティティを直接 API に使わない理由を説明してください。

**回答**

エンティティを直接返すと、パスワードのハッシュなど内部の項目まで漏れる恐れがあります。DB のスキーマ変更が API の変更になってしまうこともあります。DTO にすると、公開する項目と入力の検証を API ごとに決められます。


### Q11. グローバル例外ハンドリング

各 Controller で try-catch する場合と比較した利点を説明してください。

**回答**

各 Controller で try-catch すると、エラー応答の形式が揃わず、記録が重複し、書き忘れも起きます。グローバル例外ハンドラに集めると、エラー応答を統一できます。予期しない例外は 1 か所で ERROR として 1 回だけ記録できます。


### Q12. MyBatis vs JPA

以下の観点で違いを説明してください。

- SQL 制御
- 学習コスト

**回答**

MyBatis は SQL を自分で書くので、制御しやすく、チューニングもしやすいです。JPA は SQL を自動生成するので、記述量は減りますが、生成される SQL が見えにくくなりN+1問題になりやすくなる。

MyBatisはSQLが書ければすぐ使えるので学習コストは低め。JPA のほうが高いです(永続化コンテキスト、遅延ロードなど)。


### Q13. 環境ごとの設定管理

プロファイルの仕組みと、環境ごとに設定を分ける理由を説明してください。

**回答**

Spring のプロファイルで、開発や本番環境ごとに設定を切り替えます。環境ごとに分ける理由は、接続先、ログの量、機密情報などが環境で異なるからです。分けておけばコードを変えずに同じ成果物を各環境に配置できる。本番だけ設定を誤るといった事故も防ぎやすい。


### Q14. Flyway(DB マイグレーション)

マイグレーションツールを使う理由を説明してください。(直接 ALTER TABLE しない理由)

**回答**

直接 ALTER TABLE すると、環境ごとに構造ズレてしまうため、誰がいつ何を変えたか追えません。Flyway は、 SQL を順に適用して、履歴を管理します。どの環境でも同じ状態を再現できて、レビューもできます。


### Q15. Axios インターセプター

インターセプターとは何か説明してください。また、これが無い場合の問題点も述べてください。

**回答**

インターセプターとは、全リクエスト・レスポンスに共通の処理を差し込む仕組みです。

これが無いと、各 API 呼び出しに同じ処理を書くことになり、書き忘れや不整合が起きます。


## 第3章: フロントエンド設計(6 問)

### Q16. React Context

なぜ props ではなく Context が選ばれたのか説明してください。また、適切なケース / 不適切なケースも述べてください。

**回答**

認証状態や通知は、多くのコンポーネントが使います。props で何段も使わない部品を渡すとバケツリレーになるので、必要な部品を直接渡す　Context にします。

適切なのは、アプリ全体で共有し、頻繁には変わらない値です。不適切なのは、頻繁に変わる値や一部の部品だけが使う値です。


### Q17. カスタムフック

なぜロジックをコンポーネントではなくフックに分離するのか説明してください。

**回答**

画面(表示)とロジック(状態や通信)を分けると、再利用とテストがしやすくなり、コンポーネントは見た目に集中でき、同じロジックを複数の画面で使えます。


### Q18. コンポーネント設計

良いコンポーネント分割とは何か、具体例を挙げて説明してください。

**回答**

良い分割は、1 つの部品が 1 つの責務を持ち、再利用できることです。例として、`FollowButton` は「共通部品」としてフォロー・解除の状態を持ち、プロフィールや一覧など複数の画面で使われます。`PostCard` は投稿 1 件の表示といいねを担当します。


### Q19. TypeScript の型安全性

型のメリットと、AI コードレビュー時の利点を説明してください。

**回答**

型があると、実行前にバグ(項目名の間違い、null の見落とし)を検出できます。AI が書いたコードのレビューでは、型エラーという機械的な裏付けがあるので、判断が速くなります。レビューする側も型を見れば関数の入出力の意図が分かる。


### Q20. SPA ルーティング

従来の Web との違いを説明し、「直接 URL で 404 になる問題」の原因と対策を述べてください。

**回答**

従来の Web は、URL ごとにサーバーが HTML を返します。SPA は 1 つの HTML を読み込み、ブラウザ側で画面を切り替えます。

直接 URL を開くと 404 になる原因は、サーバーに　そのパスのファイルを探すが存在しないためです。対策は、サーバー(Nginx など)で、存在しないパスを `index.html` に返すことです。


### Q21. 楽観的 UI 更新

以下を比較してください。

- サーバー応答後に更新
- 楽観的更新

そして、どちらが適切か理由付きで答えてください。

**回答**

「サーバー応答後に更新」は確実ですが、待ち時間が掛かる。
「楽観的更新」は即座に反映され、失敗したら元に戻します。

いいね・フォローのように、失敗が少なく、元に戻せる操作には楽観的更新が適切です。


## 第4章: インフラとデプロイ(5 問)

### Q22. Docker / docker-compose

Docker の概要と、ローカルインストールとの違いを説明してください。

**回答**

Docker は、アプリと依存を「コンテナ」にまとめて動かす仕組みです。docker-composeは複数のコンテナを1つの設定ファイルでまとめて起動する。

ローカルへ直接インストールする場合と違いは、環境を汚さず、誰でも同じ状態で起動できます。


### Q23. AWS 基本サービス

EC2 / RDS / ALB / S3 の役割と分離理由を説明してください。

**回答**

役割は次のとおりです。

EC2は、アプリを動かす計算資源。
RDSは、マネージドな DB(バックアップ、パッチ)。
ALBは、負荷分散と HTTPS の終端。
S3は、画像のオブジェクトストレージ。

分離するのは、障害や負荷が独立し、それぞれを別々にスケール・保護できるからです。


### Q24. IaC(Terraform)

手動構築との違いとメリットを説明してください。

**回答**

Terraform はインフラをコードにします。手動構築と違い、再現できて、差分をレビューでき、履歴が残ります。


### Q25. 環境変数と機密情報

ソースコードに直接書く問題点と、安全な管理方法を説明してください。

**回答**

ソースコードに直接書くと、リポジトリの履歴に残って漏れます。

環境変数で渡し(`.env` は git に入れず、`.env.example` だけを置く)、本番では AWSのパラメータストアやSecrets Manager などを使います。


### Q26. 構造化ログ

JSON ログの利点と、MDC(requestId / userId)の役割を説明してください。

**回答**

JSON ログは、機械が項目で検索・集計でき、アラートにも使えます。

MDC は、リクエスト中の全ログに `request_id` と `user_id` を自動で付ける仕組みです。`request_id` で 1 リクエストのログを追え、`user_id` で誰の操作で問題が起きたかを特定できる。


## 第5章: テストと品質保証(5 問)

### Q27. テストの種類

以下の違いと具体例を説明してください。

- 単体テスト
- 結合テスト
- E2E テスト

**回答**

単体テストは、1 つのクラスを、依存をモックして検証します(例:文字数制限のチェック関数)。
結合テストは、複数の層を実際の DB(Testcontainers の PostgreSQL)でつなげて検証します(例:  投稿ボタン→API→DBの連携)。
E2E テストは、ブラウザから実際の画面操作で検証します。(例:　ログイン → 投稿 → タイムラインに表示)


### Q28. モック(テストダブル)

モックの利点と注意点を説明してください。

**回答**

モックの利点は、外部依存を切り離し、速く決定的にテストできることです。

注意点は、モックの振る舞いが現実とずれると、本物では失敗するのにテストが通ってしまうことです。モックを多用しすぎると、実装の詳細に縛られます。


### Q29. 境界値とエッジケース

「1〜280 文字制約」のテストケースを境界値分析で説明してください。

**回答**

境界値分析では、境界とその両隣を試します。

0 文字は不正、1 文字は正常、280 文字は正常、281 文字は不正です。
加えて、空白だけ、改行を含む、全角・絵文字もケースにします。


### Q30. テストカバレッジ

カバレッジの意味と限界を説明してください。「100% = バグなし」は正しいかも答えてください。

**回答**

カバレッジは、テストが実行したコードの割合です。

限界は、実行されたことしか分からず、結果が正しいかは保証されないことです。

「100% = バグなし」は正しくありません。アサーションのないテストでも 100% にできますし、仕様の漏れや組み合わせの不具合は見つかりません。


### Q31. フロントエンドテスト戦略

Testing Library の思想と、その利点を説明してください。

**回答**

Testing Library の思想は、「ユーザーが見るもの・操作するもの」でテストすることです。内部の実装ではなく、画面の文字やラベルで検証します。

実装の詳細に依存しないので、内部をリファクタリングで壊れにくく、アクセシビリティも保たれます。


## 第6章: 設計原則と実務判断(5 問)

### Q32. N+1 問題

概念と、タイムライン例で説明してください。

**回答**

N+1 問題は、1 回の取得のあとに、結果の件数分(N)の追加クエリが走ることで、合計1+N回になってしまう現象です。

タイムラインでは、投稿 20 件を取得したあと、投稿ごとに投稿者・いいね数・画像を引くと、1+20×3 回のクエリになります。


### Q33. ページネーション

必要な理由と、代表的な 2 方式を比較してください。

**回答**

全件を返すと遅く、重いので、ページネーションが必要です。

| | オフセット方式 | カーソル方式 |
| --- | --- | --- |
| 方法 | `LIMIT/OFFSET` | 最後の項目を基準に続きを取る |
| 利点 | 実装が簡単、ページ番号に飛べる | 追加・削除でずれない、深いページも速い |
| 欠点 | データが変わるとずれる、深いと遅い | 任意のページへ飛べない |

タイムラインのように常に増える一覧には、カーソル方式が向いています。このアプリは、カーソル方式です。


### Q34. 画像アップロード設計

DB 保存と S3 保存の違いと利点を説明してください。

**回答**

DB に画像を保存すると、DB が肥大化し、バックアップと配信が重くなります。S3 に置けば、安価で、配信しやすく、DB は URL(キー)だけを持ちます。


### Q35. API バージョニング

代表的な方式と特徴を説明してください。

**回答**

代表的な方式は 3 つです。

URLパス方式は、分かりやすく、広く使われます。URLが変わる。
ヘッダー方式は、URL がきれいですが、扱いにくいです。
クエリ方式は、簡単ですが、キャッシュや運用で不利です。


### Q36. 技術選定
判断基準を説明し、React+ Spring Boot + PostgreSQL を例に具体化してください。

**回答**

判断基準は、要件への適合、チームの習熟度、エコシステムと保守性、運用コストです。このアプリでの具体化は次のとおりです。

Reactは、画面を部品化でき、状態の変化に応じて必要な部分だけ再描画できる。エコシステムが大きく、TypeScript で型安全に書ける。タイムラインのような更新の多い画面に向く。
Spring Bootは、認証・入力検証・トランザクション・DB 連携が標準で揃い、Java の静的型付けで堅く保てる。LTS があり保守しやすい。
PostgreSQLは、信頼性が高く、制約とトランザクションで整合性を守れる。ライセンスが自由で、インデックスなど検索の機能が豊富。
